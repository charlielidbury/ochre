## Running

```
./setup.sh                 # once, online (a few minutes; Aeneas's Lean library takes ~8 min to build)
./grade.sh                 # grades the package itself: FAILs on the skeleton, naming the 23 holes
./grade.sh SOLUTION_DIR    # grades another directory (the authoritative grade: run it from the repo)
./make-sandbox.sh DEST     # a fresh sandbox for one trial
```

`grade.sh` never builds in the graded directory. It copies the pristine skeleton (from the repo, or from `grader/orig` inside a sandbox) to `.grade/work`, overlays exactly the files in `SOLUTION_FILES`, and then: checks the FIXED regions with `../../common/check_fixed.py`; scans the solution files for holes and forbidden constructs; runs `cargo test`; regenerates the model with `translate.sh`; runs `lake build`; and finally writes `GradeCheck.lean`, which restates every FIXED theorem in a context no solution code can influence (the skeleton's names opened, not the namespace entered) and checks the solution's theorem against it, plus `#print axioms` for each (only `propext`, `Classical.choice`, `Quot.sound` allowed). The last line starts with `GRADE: PASS` or `GRADE: FAIL`.

Forbidden constructs are listed in `ASSIGNMENT.md` §6 and implemented in `grader/package.json`. Beyond the protocol's list for `aeneas`, the grader also forbids, in Lean, new notation/macros/elaborators, `export`, instances and `unif_hint` (each can change how a FIXED statement elaborates), and `#eval`/`run_cmd`-style commands; in Rust, copying (`clone`, `to_vec`, ...), `cfg`, `macro_rules!`, `include!` and raw pointers.

## The sandbox

`make-sandbox.sh DEST` copies, by explicit list, the package's own sources (and a pristine copy of them in `grader/orig`), `check_fixed.py`, `vendor/aeneas` (Aeneas's `backends/lean` pre-built, `documentation/`, `docs/user/`, the tutorial from `tests/lean/Tutorial` and `tests/src/tutorial`, README, licence), `vendor/charon-docs`, `lean/.lake/packages` (Mathlib and dependencies, pre-built), and the Lean toolchain into `DEST/.elan`. `DEST/.tools` is a symlink to the Nix store path of the tools, and `DEST/.tools-closure` lists every store path the sandbox needs (the tools' closure plus the store paths NixOS's elan patches into the Lean toolchain). **The runner must expose exactly those store paths and no others**: this host's store also holds the full Aeneas source (the flake input), whose `tests/lean/Hashmap/` is Aeneas's own verified hashmap.

What the agent can and cannot reach (checked by `make-sandbox.sh`, which fails if an exclusion is violated):
- Not reachable: Aeneas's `tests/` (including `tests/lean/Hashmap/{Funs,Properties}.lean` and `tests/src/hashmap.rs`); none of the definitions distinctive of Aeneas's hashmap test (`allocate_slots`, `move_elements_from_list`, `insert_no_resize`, `try_resize`, `hash_key`) occurs in any `.lean` file of the sandbox, Mathlib or Lean core included; no `.lean` file in the tools closure; nothing from this repository outside the package (no Ochr sources, paper, notes, `competitors/`, `_reference/`).
- Reachable, as general library content every Lean or Rust condition has: Lean core's `Std.HashMap` and `List.mergeSort` with their lemmas, Mathlib's `List.Sorted`/`List.insertionSort`/`List.mergeSort` lemmas (57 files with hash-map or sort in the name across Mathlib, Batteries and Lean core); the Rust standard library's sources in the toolchain's `rust-src` component, including its (unverified) `HashMap` and slice sorts (`core/src/slice/sort/unstable/quicksort.rs`). One docstring in Aeneas's library (`Aeneas/Tactic/Step/Step.lean`, the `step` tactic's documentation) shows the *statement* shape of a `hashmap_insert_spec` with a ghost model, as an example of ghost variables; it contains no proof.

Validated on 2026-09-30: a sandbox built by `make-sandbox.sh` grades on its own with no network (`unshare -rn`) and an empty environment (`env -i PATH=$DEST/.tools/bin`).

## Fairness notes for this condition

- `get_mut` returns `&mut u64` and panics on an absent key, as the design requires (Ochr cannot return a borrow inside an `Option`). Aeneas handles `Option<&mut u64>` well, so the natural Rust API would differ; the panicking version costs Aeneas nothing extra (the precondition simply rules out the `fail` branch).
- `new` takes `cap: usize`, not `u64`. Aeneas models `usize` with a platform width of 32 or 64 bits, so with `u64` the model's `Vec` could not hold `cap` buckets for every `cap`, and H1/H4/H11 would need an extra hypothesis `cap ≤ usize::MAX`, which the SPEC does not allow. `usize` is also the idiomatic Rust type for a capacity. `bucket_index` casts `cap` to `u64` (exact) and the remainder back to `usize` (exact, since it is below `cap`).
- `len` is a `u64` field, so `insert` can overflow; the SPEC's allowance `len(m) < 2⁶⁴ − 1` is the hypothesis `hlen` on H2, H5–H7, H12, H14, H15. H16 is stated without it (and without running `insert`), which is stronger than the SPEC.
- Aeneas renames the method `len` to `HashMap.impl.len`, because `HashMap.len` is the field's projection. The statements use the generated name; ASSIGNMENT.md explains it.
- Every statement is total (`⦃ ⦄` is Aeneas's total-correctness triple), as the protocol requires; the agent proves termination of recursive list functions and loops.
- The grader's instance ban is slightly stricter than the protocol's list; an honest solution has no reason to declare instances.
