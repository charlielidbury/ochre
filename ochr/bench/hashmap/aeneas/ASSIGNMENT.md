# Coursework: a verified hash map in Rust, with Aeneas

## 1. Overview

Implement a fixed-capacity hash map with separate chaining in Rust, operating in place, and prove that it behaves like a finite map, as observed through `get` and `len`.

You verify your Rust with **Aeneas**. Charon compiles your crate to an intermediate language (LLBC), Aeneas translates that into a pure functional model in Lean 4, and you prove the properties in Lean about that model. The model is regenerated from your Rust every time you grade, so the proofs are always about the code you wrote.

You are done when `./grade.sh` prints `GRADE: PASS` and exits with status 0 (section 8).

## 3. What to build

### 3.1 Representation (FIXED, in `rust/src/lib.rs`)

```rust
pub enum List {
    Cons(u64, u64, Box<List>),
    Nil,
}

pub struct HashMap {
    slots: Vec<List>,
    len: u64,
}

pub fn bucket_index(key: u64, cap: usize) -> usize {
    (key % (cap as u64)) as usize
}
```

A map with capacity `c` (where `c ≥ 1`) has `slots.len() == c` buckets. The capacity is chosen by `new` and never changes: there is no resize. Each bucket is a singly linked list of (key, value) entries, each node owned by the previous one. The entry for key `k` lives in bucket `slots[bucket_index(k, c)]`, that is `slots[k mod c]`; `bucket_index` is the only hash function. `len` is the number of entries. Keys and values are `u64`.

### 3.2 Operations (FIXED signatures; you write the bodies)

| Operation | Signature | Precondition |
|---|---|---|
| new | `pub fn new(cap: usize) -> HashMap` | `cap > 0` |
| len | `pub fn len(&self) -> u64` | |
| get | `pub fn get(&self, key: u64) -> Option<u64>` | |
| insert | `pub fn insert(&mut self, key: u64, value: u64) -> Option<u64>` | |
| remove | `pub fn remove(&mut self, key: u64) -> Option<u64>` | |
| get_mut | `pub fn get_mut(&mut self, key: u64) -> &mut u64` | `key` is present |

- `new(c)` is an empty map with `c` empty buckets and `len = 0`.
- `len(m)` is the number of keys in the map.
- `get(m, k)` is `Some(v)` if `k` is bound to `v`, and `None` otherwise.
- `insert(m, k, v)` binds `k` to `v` and returns the value `k` was bound to before, or `None`.
- `remove(m, k)` unbinds `k` and returns the value it was bound to, or `None`.
- `get_mut(m, k)` returns a mutable borrow of the value stored for `k`. It requires `k` to be present, and may panic otherwise.

You may add private helper functions, methods and types, anywhere outside the FIXED regions.

### 3.3 Algorithm requirements (checked by a human reader, not by the grader)

- **A1 (hashing).** Every operation on key `k` reads or changes only the bucket `slots[bucket_index(k, c)]` and the `len` field. No operation scans other buckets.
- **A2 (in place).** Operations change the map in place. No operation copies the table or a bucket, or rebuilds a bucket from a copy. A new entry may go at either end of its bucket. `remove` unlinks the node.
- **A3 (nothing extra).** No auxiliary structure (a second table, a list of keys, a cache), no resizing, and no library map, set or association list.

## 4. What to prove

The properties are in `lean/Hashmap/Properties.lean`, about the Aeneas model of your code: `HashMap.new`, `HashMap.impl.len`, `HashMap.get`, `HashMap.insert`, `HashMap.remove` and `HashMap.get_mut` in namespace `hashmap`. The statements are FIXED; you replace each `sorry`.

How to read them:
- `f x ⦃ (r : T) => P r ⦄` is Aeneas's total-correctness triple: `f x` terminates without panicking, and its result `r` satisfies `P r`. With two binders, `⦃ (r : T) (m' : HashMap) => ... ⦄` destructures a pair.
- A Rust function taking `&mut self` returns the new map as the last component of its result: `HashMap.insert m k v` returns `(old, m')`.
- `HashMap.get_mut m k` returns the current value `x` and a backward function `back`: `back w` is the map after `*m.get_mut(k) = w`, once the borrow ends. Below, `m[k ≔ w]` means `back w`.
- The method `len` translates to `HashMap.impl.len`: Aeneas renames it because `HashMap.len` is already the projection of the field `len`.
- Observations are `Result` values: `HashMap.get m k = ok (some v)` says `get` succeeds and returns `Some(v)`.

**The invariant.** Define `Inv (m : HashMap) : Prop` (a hole in the FIXED region `Inv`). It may be any predicate that makes the theorems below provable.

The properties, with the names of the theorems:

| Id | Theorem | Says |
|---|---|---|
| H1 | `H1_inv_new` | `new c` succeeds (for `c > 0`) and satisfies `Inv`. |
| H2 | `H2_inv_insert` | `insert` preserves `Inv`. |
| H3 | `H3_inv_remove` | `remove` preserves `Inv`. |
| H4 | `H4_get_new` | `get (new c) k = None` for every `k`. |
| H5 | `H5_get_insert_same` | After `insert m k v`, `get m' k = Some v`. |
| H6 | `H6_get_insert_other` | After `insert m k v`, `get m' k' = get m k'` for `k' ≠ k`. |
| H7 | `H7_insert_returns_old` | `insert m k v` returns `get m k`. |
| H8 | `H8_get_remove_same` | After `remove m k`, `get m' k = None`. |
| H9 | `H9_get_remove_other` | After `remove m k`, `get m' k' = get m k'` for `k' ≠ k`. |
| H10 | `H10_remove_returns_old` | `remove m k` returns `get m k`. |
| H11 | `H11_len_new` | `len (new c) = 0`. |
| H12 | `H12_len_insert` | `len m' = len m + 1` if `get m k = None`, else `len m' = len m`. |
| H13 | `H13_len_remove` | `len m' + 1 = len m` if `get m k ≠ None`, else `len m' = len m`. |
| H14 | `H14_get_mut_get` | If `k` is present: `get m[k ≔ w] k' = get m₂ k'` for every `k'`, where `insert m k w` gives `m₂`. |
| H15 | `H15_get_mut_len` | If `k` is present: `len m[k ≔ w] = len m₂`. |
| H16 | `H16_get_mut_inv` | If `k` is present: `Inv m[k ≔ w]`. |

H2 and H5 to H16 assume `Inv m`. The ones that run `insert` (H2, H5, H6, H7, H12, H14, H15) also assume `len m < 2^64 − 1` (the hypothesis `hlen`), because `len` is a `u64` and Rust's `+ 1` panics on overflow. No other hypotheses are allowed. Two properties of the system-neutral assignment are not stated here, because the Rust types already guarantee them: that `get` and `len` leave the map unchanged (they take `&self`, and their models return no new map).

In `Properties.lean` you may add definitions and lemmas anywhere outside the FIXED regions. Tagging your own lemmas `@[step]` lets the `step` tactic use them.

## 5. Tests

`rust/tests/spec.rs` (FIXED) holds the test vectors, transcribed mechanically. Each test starts from `HashMap::new(cap)` and applies a sequence of operations, checking each result and `len()` after each operation:
- `scripted`: on `new(4)`, written by hand. It covers collisions (several keys in one bucket), overwriting with the previous value returned, removing a key at the head, middle and end of a bucket, removing an absent key, removing twice, writing through `get_mut` then reading with `get` (the same key and a neighbour in the same bucket), `insert` after `get_mut`, and re-inserting a removed key.
- `random_cap1`, `random_cap3`, `random_cap4`, `random_cap7`: 50 pseudo-random operations each, over a key space about three times the capacity. With capacity 1 every key shares one bucket.

Run them with `cd rust && cargo test` (grade.sh runs them too).

## 6. What is provided, and what is forbidden

Provided: everything in this directory (section 2).

Your solution is the two files listed in `SOLUTION_FILES`: `rust/src/lib.rs` and `lean/Hashmap/Properties.lean`. Edit them only outside the FIXED regions (the text between a `FIXED-BEGIN <id>` comment and the matching `FIXED-END <id>` comment, both included, must stay byte-identical). grade.sh takes exactly these two files from your directory and everything else from a pristine copy, so changes anywhere else (other files you create, the lakefile, `Cargo.toml`, the vendored libraries, the generated model) have no effect on grading: put all your helper functions, definitions and lemmas in the two solution files.

Forbidden in your Rust (outside comments and strings):
- `todo!`, `unimplemented!` (holes);
- `unsafe`, raw pointers, `transmute`, `extern`;
- library collections (`std::collections`, `BTreeMap`, `HashSet`, `VecDeque`, ...) and library sorting or selection (`.sort*()`, `select_nth*`);
- copying: `clone`, `Clone`, `cloned`, `to_vec`, `to_owned`, `copy_from_slice`, `clone_from_slice`;
- `#[charon::...]` and `#[aeneas::...]` attributes, crate-level attributes `#![...]`, conditional compilation (`cfg`), `include!`, `macro_rules!`.

Forbidden in your Lean (outside comments and strings):
- `sorry` (holes), `admit`, `axiom`;
- `native_decide`, `decide +native`, `ofReduceBool`, `implemented_by`, `extern`, `unsafe`, `opaque`, `partial`;
- new syntax, notation, macros or elaborators (`macro`, `syntax`, `notation`, `infix`, `elab`, ...), `export`, instances (`instance`, `attribute [instance]`, `deriving instance`) and `unif_hint`, because they can change what a FIXED statement means;
- `#eval`, `#exit`, `run_cmd`, `run_tac`, `run_elab`, `run_meta`, `initialize`, and `debug.*` options.

Also forbidden: any other way of making a FIXED statement mean something else, or of making the proofs depend on axioms other than `propext`, `Classical.choice` and `Quot.sound` (grade.sh checks the axioms of every theorem).

## 7. Aeneas notes

- Machine arithmetic panics on overflow, in Rust and in the model (`fail`). `u64` addition is checked; so is `usize`.
- `usize` in the model has a platform-dependent width (32 or 64 bits); `cap as u64` is exact, and `k % cap` is below `cap`, so `bucket_index` never truncates.
- Recursive functions and loops translate to definitions by `partial_fixpoint` and `loop`; a total-correctness triple about them needs a termination argument (induction on the list, or a loop measure; see `proof-strategies.md`).

## 8. How to check your work

Run `./grade.sh` in this directory. It:
1. checks that every FIXED region is byte-identical to the original;
2. lays your two solution files over a pristine copy of the skeleton in `.grade/work`;
3. scans them for holes and forbidden constructs (section 6);
4. runs the tests (`cargo test`);
5. regenerates the Lean model from your Rust (Charon, then Aeneas);
6. builds the Lean project (`lake build`);
7. restates every FIXED theorem in a fresh file, checks that your proof proves exactly that statement, and checks the axioms it depends on.

Each problem is printed on its own line, with the hole or construct it found; logs are in `.grade/`. The last line is the verdict: `GRADE: PASS (...)` or `GRADE: FAIL (...)`, followed by your solution's size (non-blank lines outside the FIXED regions; a secondary measure, reported for information). The exit status is 0 exactly when the verdict is `GRADE: PASS`.
