# Does the Aeneas toolchain swallow the splice?

Yes, completely, on the first try, with no errors and no warnings, into both the
Lean and the Rocq backends.

Run `./translate.sh` to reproduce. It builds the pinned tools with nix, runs
Charon (Rust → LLBC) and Aeneas (LLBC → Lean/Rocq) over both variants, and
diffs the output.

## What was run

| | |
|---|---|
| Charon | `0.1.236`, rev `f5a61c8f2cb695213b427ab696f8088f357b5dea` (nix store `dwx4921c27pd177dxg7vjq90pnknbrd5-charon`) |
| Aeneas | `937ff0d` (nix store `ybmvbyp2fird43nmp52923aggd7f44kc-ocaml5.2.1-aeneas-0.1.0`) |
| Date | 2026-08-20 |

Two things that cost time and are worth writing down:

- **Charon must be the revision Aeneas pins**, not Charon's `main`. `main` was
  `0.1.237`; Aeneas's `flake.lock` pins `0.1.236`, and mixing them risks an LLBC
  format mismatch.
- **`--preset=aeneas` is mandatory.** Without it Charon produces a perfectly
  good `.llbc` that Aeneas then refuses outright: *"the serialized crate was
  generated by Charon without the `--preset=aeneas` option."*

The invocation, per variant:

```
charon rustc --preset=aeneas --dest-file hashmap_$V.llbc \
  -- --edition 2021 --crate-type=rlib --crate-name hashmap $SRC
aeneas -backend lean -split-files -loops-to-rec -dest lean/$V hashmap_$V.llbc
```

`-split-files -loops-to-rec` are the arguments the vendored file's own `//@`
header asks for.

## The invocation is validated against upstream

`../current/hashmap.rs` is byte-identical to upstream `main`'s
`tests/src/hashmap.rs` today, and the Lean this produces for it is **identical
to the `tests/lean/Hashmap/Funs.lean` upstream has checked in** — every line,
modulo the source-path comments and the import name. So the baseline column
below is not "what my invocation happened to produce", it is upstream's own
output, and the splice column is directly comparable to it.

## The result

Aeneas reports exactly the same inventory for both: 40 prepasses, 1 global, 13
opaque functions, 21 transparent functions, 3 trait declarations, 3 trait
impls. `Types.lean` is identical apart from source locations. `Funs.lean` is 432
lines for the baseline and 442 for the splice, and **the entire difference is
the body of one function**.

Upstream:

```lean
@[rust_loop]
def HashMap.move_elements_from_list_loop
  {T : Type} (ntable : HashMap T) (ls : AList T) : Result (HashMap T) := do
  match ls with
  | AList.Cons k v tl =>
    let ntable1 ← HashMap.insert_no_resize ntable k v
    HashMap.move_elements_from_list_loop ntable1 tl
  | AList.Nil => ok ntable
partial_fixpoint
```

The splice:

```lean
@[rust_loop]
def HashMap.move_elements_from_list_loop
  {T : Type} (ls : AList T) (ntable : HashMap T) : Result (HashMap T) := do
  match ls with
  | AList.Cons k v tl =>
    let hash ← hash_key k
    let i := alloc.vec.Vec.len ntable.slots
    let hash_mod ← hash % i
    let (dst, index_mut_back) ←
      alloc.vec.Vec.index_mut (core.slice.index.SliceIndexUsizeSlice (AList T))
        ntable.slots hash_mod
    let (dst_head, _) := core.mem.replace dst AList.Nil
    let (rest, tl1) := core.mem.replace tl dst_head
    let i1 ← ntable.num_entries + 1#usize
    let v1 := index_mut_back (AList.Cons k v tl1)
    HashMap.move_elements_from_list_loop rest
      { ntable with num_entries := i1, slots := v1 }
  | AList.Nil => ok ntable
partial_fixpoint
```

Ten lines longer, and every construct in it already appears elsewhere in the
same generated file. The Rocq backend produces the same shape
(`generated/rocq/`), so this is not a Lean-specific accident.

Things worth pointing at in that output:

- **`Box` is gone.** `tl : AList T`, not `Box (AList T)`. Aeneas erases boxes at
  the functional-translation level, which is the whole reason this experiment
  has an interesting answer: **allocation is invisible in the generated model**,
  so making the resize allocation-free changes nothing about what has to be
  proved *because it allocates less*. It changes things only because it is a
  different function.
- **`&mut *tl` translated without complaint.** The reborrow through the box
  shows up in the LLBC as `_23 = &mut (*tl)` / `_22 = &two-phase-mut (*_23)` and
  then simply disappears into the pure model.
- **The nested `mem::replace` chain is two ordinary calls.** `core.mem.replace`
  was already a supported primitive — upstream's own `move_elements` loop uses
  it — so the splice adds no new vocabulary at all.
- **Aeneas optimised one of the three writes away.** `let (dst_head, _) :=
  core.mem.replace dst AList.Nil` discards the second component: the `AList.Nil`
  written into the destination slot is dead, because `index_mut_back (AList.Cons
  k v tl1)` overwrites it before anything reads it. The rotation that needs a
  scratch `Nil` in Rust needs none in the pure model.
- **`index_mut_back` carries the write back into the vector.** The `&mut` into
  `ntable.slots[hash_mod]` becomes a forward value plus a backward function,
  which is the core Aeneas idea and it handles this borrow exactly as it handles
  `insert_no_resize`'s.
- **No termination obligation either way.** Both are `partial_fixpoint`, which
  is newer than the ICFP'22 artifact, where `Hashmap.Clauses.fst` held
  hand-written `decreases` measures.
- **Two arithmetic obligations moved rather than appeared.** The LLBC for the
  splice carries `assert(... == false) (remainder_by_zero)` for `hash %
  slots.len()` and `assert(... == false) (overflow)` for `num_entries + 1`.
  Upstream has both too — inside `insert_no_resize`. Inlining the insert moved
  them into this function; it did not create them.
- Aeneas reordered the parameters to `(ls) (ntable)`. Cosmetic.

## What was *not* done

The generated Lean was **not typechecked by Lean**, and no proof was ported.
Both were out of scope. What can be said about the proofs is in
`../SPLICE-NOTES.md`.
