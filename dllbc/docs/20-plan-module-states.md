## The problem

Reuse today is Lean-level splicing: a library definition is a Lean `def X : Term := prog_parse { … }`, and a program that wants it either splices it (`%X`) or cites it through the identifier fallback after an `open`. Three costs:

1. Nothing checks a library definition at its definition site. `defer_check` opts it out of the program judgment (which would be the wrong judgment anyway), so an ill-typed lemma compiles green and is citable by its stated type. The reachability sweep of 2026-08-21 found ten StdLemmas entries that had *never* been checked and do not inhabit their stated types; the `chkLib` battery now embedded in `StdLemmas.lean` is a stopgap, not a design.
2. Every use site re-carries the plumbing: `open` lists naming each lemma and its type, splice markers, and the `X`/`XTy` two-defs-per-lemma convention.
3. Tooling stops at the splice boundary. A spliced term has no source positions, so hover and error spans have nothing to attach to inside it.

## The design

`prog` blocks input and output a checker state `St` (Ω's comptime bindings, `sctx`, the fn/call table, the seal-site table, and the housekeeping counters — `nextSym`, seal-site numbering). A module is a `prog` block interpreted once, at its own elaboration; its ending state is persisted, and a later block seeds from it.

Three decisions fixed in discussion:

- **Semantics = prefix splice.** "Importing `Std`" *means* "this program checks exactly as if `Std`'s chain were textually prefixed to it". The persisted state is a cache of the value that prefix produces. Because `St`/`Val` are strict first-order data in a pure language, the cache is definitionally the same value however it is reached — there is no serializer to distort it, and no fidelity test worth writing unless a *derived* (pruned/pre-normalized) cache is introduced later. The one structural requirement: seeding must mean literally "begin the walk with this `St`", the same code path as mid-program state, not a special entry mode.
- **One input state per block.** `prog` takes exactly one predecessor state, so module composition is a chain by construction. Diamond imports are structurally unrepresentable — no union operation exists, so no collision handling and no refusal logic. Counters thread through the state, so the next block mints σs and seal sites where the last one stopped. Merges are consciously deferred.
- **`fn` is the lemma form.** The signature is the stated type, the body is the proof, and the seal's audit checks the body against the signature at elaboration. Never `let X = (λ … : Π …)` — that is exactly what `fn` already is. This deletes the `X`/`XTy` convention: the type is the signature, written once. Parameters are lowercase where the body matches on them (see the snippet and its boundary note below); the λ/`elim` spelling remains for terms cited inside types.

## Modules are ordinary Lean values

No new namespace, no registry: `prog { … }` elaborates to a plain Lean value carrying the term and the ending state, and a consuming block takes a state value as its one argument. Lean's own `def`s, namespaces, and imports do all the bookkeeping. (Lean has no top-level destructuring `def (a, b) := …`, so the pair is a structure with projections:)

```
structure Checked where
  term : Term
  env  : St                 -- the checking machine's ending state
  exec : Except String St   -- the executing machine's (stage 6)
```

Two states, one per machine (stage 6, below): the checking walk leaves each `fn` as a sealed σ and the executing walk leaves it as a closure, and a consumer run from the checking state never enters a library body. `exec` is an `Except` because an executing walk can fail where the checking one passed (fuel, a body the signature did not promise), and that is a fact about the runtime, not a rejection of the module.

No separate provenance field. The knowledge half of provenance — what the checker knew at each binding, the point deltas hover replays — already lives inside `St` (`St.ledgers : Ledgers`), position-free, keyed by binder `Var`s and statement `Term`s. The position half — the `SpanAcc` join table (statement-term key → span) the defining elaboration currently discards — becomes a **fourth channel of `Ledgers`**, which is the record's stated purpose: three diagnostic carries were each taught to cross the seal by hand before the carry was made a unit, and a fourth channel joins by construction. Spans are stored as plain data (`module : String`, offsets as `Nat`s), never `Lean.Syntax`, so the kernel gains no elaborator imports; the machine never reads the channel, which is already licensed by `PointDelta.sctx`'s rendering-only precedent. One consequence to note where it bites: two states can be judgment-equivalent while differing in ledgers, so state-equality assertions should compare the judgment-relevant projection.

## What `StdLemmas.lean` becomes

One block (or a short chain of them), written in the surface, checked as it elaborates:

```
def std : Checked := prog {
  fn LeRefl [n] (n : Nat) -> Le n n {
    match n { Z => unit, S(k) => LeRefl(k) } };

  fn LeTrans [a] (a : Nat, b : Nat, c : Nat, Hab : Le a b, Hbc : Le b c) -> Le a c {
    match a { Z => unit,
      S(a2) => match b { Z => botElim (Le (S a2) c) Hab,
        S(b2) => match c { Z => botElim (Le (S a2) Z) Hbc,
          S(c2) => LeTrans(a2, b2, c2, Hab, Hbc) } } } };

  ()
}
```

Both of these CHECK TODAY (probed 2026-08-21, worktree at the tier-cut branch): the `fn` sugar derives the dependent motive from the signature, the self-call becomes `Ih`, and — the notable part — matching `b` ⇜-refines `Hab`/`Hbc`'s types per arm, so the machine's state does the job CIC needs the convoy pattern for. No motive is written anywhere; compare the current triple-`elim` `LeTrans` with three hand-written motives.

The boundary: match-style lemmas take LOWERCASE (runtime) parameters — the fence refuses `match` on a comptime binder, and a comptime split is `elim` by design. Consumption changes shape but not power for PROOF-producing lemmas: today a lemma is usually an inline spine in a ⇝ position (a carve's evidence slot, a proof argument) reduced by the pure engine; under the `fn` form the consumer calls the lemma and binds the result — an opaque σ at the return type — and cites the binding. That serves identically, because proofs are consumed by TYPE (the slot converts `Le k3 …`, never the proof's body). What genuinely cannot move to `fn`+`match` is anything whose RESULT participates in conversion — the spec functions (`Set`, `Count`, `Len`) and type-level terms (`OptP`) that appear inside types and must ⇝-reduce there. Those are not lemmas and keep the λ/`elim` spelling. Making `match` one construct across both arrows is the standing north star, and this is fresh evidence of its payoff — not part of this plan.

Elaborating this block **is** the check: a body that does not inhabit its signature is a squiggle at the offending syntax, at definition time, like any `prog{}` today. Chaining is function application:

```
def sortLemmas : Checked := prog (std) {
  fn CountConsHit (…) -> … { … };
  ()
}
```

## What a consumer looks like

```
def quicksortChain : Checked := prog (sortLemmas) {
  fn UseTrans (a : Nat, b : Nat, c : Nat, p : Le a b, q : Le b c) -> Le a c {
    LeTrans(a, b, c, p, q) };
  () }
```

No `open` list, no `%` splice: `LeTrans` resolves against the seed state's comptime environment (checked before the existing Lean-constant fallback, which can then retire). The call is checked against `LeTrans`'s signature exactly as any `fn` call is — the signature the definition site already verified the body against. A no-argument `prog{}` seeds the empty state, so existing programs are the degenerate case.

The one piece of real machinery: `prog (sortLemmas) { … }` checks at elaboration time, so the elaborator must obtain the **value** of the seed expression during elaboration — `evalExpr`-style evaluation of a compiled constant, the same machinery `native_decide` and the in-elaborator `checkProgram` already use. Cross-file this is a native call (memoizable per session); same-file it falls back to the interpreter. By purity, evaluate-on-demand is indistinguishable from any cached store.

## Why the mechanism is cheap in Lean

- A Lean elab runs with the full `Environment` of every import — constants all natively evaluable. `def std : Checked := …` is an ordinary constant, and the consuming elab evaluates it on demand. **What the `.olean` persists is NOT the state but the recipe**: the constant's value is `Checked.seeded <seed> <term> <hints> <spans>` (there is no `ToExpr St`), so forcing it RE-DERIVES both walks — the checking walk over the whole chain, audits included, i.e. the library is re-verified in every process that forces the constant. Measured 2026-08-22 (native, `lake build`; the closed constant is computed at the module's `.so` initialisation, so this is a per-process cost): the audited checking walk over the 110-fn chain is **0.83 s**, the executing twin's walk is negligible beside it, and a consumer test module (`Tests/ModuleStates.lean`, seven seeded blocks and a dozen `native_decide`s against the chain) builds in **2.2–2.7 s** end to end. The editor pays the same: `lake setup-file` hands the server every `dllbc_Dllbc_*.so` plugin, StdChain's included. A figure of ~19 s circulated for this cost; it is the INTERPRETED walk (`lake env lean`, ~25×) and is not what any build or editor session pays. So re-derivation is free at human scale and no cache is built. The alternative was measured rather than argued (probe 2026-08-22, a `trusted` flag on `St` making `checkRFnBody` return before the frame is opened, applied and reverted): the audit-skipping walk over the chain takes **20 ms** against the audited walk's 855 ms — the audits ARE the cost, the seals' own mints are nothing — and its state is NOT the audited one. The seal's audit frame carries the fresh supplies and the site table OUT (`checkRFnBody` restores Ω and `sctx` from the saved state but advances `nextSym`/`nextLoan`/`nextGroup` and keeps `sealSites`, so that no later mint collides with a σ a nested seal recorded), and the audit's mints are interleaved with the seals' own: `nextSym` ends at 3309 audited vs 110 trusted, `nextGroup` 10 vs 0, and the first fn already differs — `LeRefl ↦ σ₃` audited (its audit minted three σs before its seal minted one) vs `σ₀` trusted — so `env`, `sctx`, `fsig` and `sealSites` all differ by a renumbering, not by an offset. Making that vanish means the audit frame restoring the supplies and the site table as well as Ω, a kernel change to a documented decision, bought for under a second per process; not taken. A persistent environment extension holding the `St` values stays in reserve for the day a chain's walk measures in tens of seconds natively.
- **Info trees** (hover data) are per-file and not persisted. Cross-file hover therefore answers from the ledgers (knowledge + spans) carried inside `env` — the same way Lean shows types and docstrings for imported constants. Hover at a use site of `LeTrans` shows its signature (and can show the defining source, since the defining module elaborated real syntax at real positions in its own file).
- `StdLemmas` already imports `ElabCheck`, so none of this needs a layering change; the library sits above the checker today.

## What this deletes

- The `chkLib` battery in `StdLemmas.lean` and every scattered `chkL` check of library entries — definition-site checking subsumes them.
- The `X`/`XTy` two-defs-per-lemma convention (the signature is the type).
- `defer_check` on the library, the per-use-site `open` lists, and the `%` splices for library terms.
- The identifier-fallback resolution channel for library lemmas (kept only for genuinely Lean-side terms, if any remain).

A seed binding cited in a TYPE reduces (evaluate-by-environment), which is what consumers need — so only the formers are bound and the `XRaw` terms are not bound at all. The `Std` aliases (`Add`, `Le`, `Count`, `Len`, `Eqb`, `Leb`, `Take`, `Drop`) resolve bare everywhere; `Append` in the fn section is the constant (the binding comes after it).

   The port measured the `fn`-lemma boundary precisely, across ten independent transcription agents:
   * **Consumption discipline decides P1.** `Le`-style lemmas (proofs consumed by type: refinement, botElim) rewrite natively. `Id`-lemmas whose recursive step composes through `j`/`IdCongr`/`IdTrans` cannot: `j` consumes its witness by value, a `fn`'s `Ih` is an opaque existential, and matching `Refl` on it is stuck rigid-rigid. Recursive `Id`-arithmetic stays wrapped under the current kernel.
   * `fnElab` lowers `[k]` recursion to `natRec`/`listRec` only — array-shaped lemmas cannot go native regardless of spelling. Non-recursive matches (Σ-projections) have no scrutinee-type restriction.
   * A named capital Σ binder makes its component comptime, and a comptime arm binder cannot be returned as a runtime result — `Ub`/`Lb` projections stay wrapped while `Sorted`/`Bound`'s anonymous-product cousins go native.
   * A proof premise used more than once per branch must be CAPITAL (a lowercase proof is a linear runtime resource, one read per path), Π-typed or not.
   * An all-comptime `fn` body cannot call a sibling `fn` (a call is ⇒-only; the body is ⇝ throughout); pure application of a raw constant is fine. In mixed bodies, a sibling call cannot nest inside a juxtaposed pure application — bind it with a lowercase `let` first. Self-calls are exempt (they become `Ih`).
   * Known diagnostics gap: this last failure class reports with no span, pointing at the block's first `fn`.

## Consumer migration playbook

Written from the pilot (`Tests/ArrCatIota.lean`, 2026-08-24): one file migrated end to end, every behavioural claim preserved, `grep StdLemmas` empty, full build green. The remaining consumer files follow this recipe; the gotchas at the end are the things the pilot actually hit, in the order it hit them.

### The recipe

1. **Scope the dependency first.** Grep the file for its `open Dllbc.StdLemmas (…)` list, then grep each opened name — files over-open (ArrCatIota opened five lemmas, used one). Only the used ones need translations; the rest vanish with the `open`.
2. **Imports.** `import Dllbc.StdLemmas` → `import Dllbc.StdChain`; delete the `open`. StdChain brings `ElabCheck` (the `prog (…) { }` elaborator) transitively.
3. **Accepted programs that cite lemmas → seeded goldens.** `def x : Term := prog{ … }` becomes `def x : Checked := prog (Dllbc.std) { … }`. Inside, each inline lemma spine becomes call-and-bind: `LeAddRaw i (S r)` in a carve's evidence slot becomes `let h1 = LeAdd(i, S r);` above the carve and `| h1 |` in the slot — the call binds an opaque σ at the lemma's return type and the slot consumes it by TYPE. Verified in the pilot: works inside a `fn` body, as a lowercase (linear) binding read once; the checking walk takes the signature-only call rule, the executing twin enters the chain body and computes the proof concretely.
4. **Keep the old `progOk` as `progOkFrom Dllbc.std x.term`** — do NOT drop it as subsumed. The golden's elaboration runs `modulePathsD`, which omits BOTH the closing `endScope` and the `Unit` return audit (a module's bindings must persist), so the elaboration is the definition-site check and `progOkFrom` is the scope-close half the old assertion also made. Two assertions, both meant.
5. **Rejects that are one-lie variants of an accepted program → marked twins** (docs/21). Mark the claim sites in the golden (`@slot` on the pin instantiation, `@exit` on the escape), mint each twin from `golden.term` (persisted pre-boundary, markers intact, calls already retargeted — the helpers' retarget is a no-op on it), assert `(twin == golden.term) = false` and `progRejectsFrom Dllbc.std twin needle`. Keep plain `prog_parse` + `progRejectsFrom` where the reject is not a mutation of any golden.
6. **Runs → the executing twin.** `runProgram`-based assertions become `runProgramFrom Dllbc.std x.term` / `progRunsToFrom`. The seeded helper drops the seed's own entries (the 110 declarations and 26 former bindings never appear) and canonicalizes, so per-binding expected values port VERBATIM — the pilot's end-to-end `p` value string is character-identical to the unseeded one.
7. **Programs with no library citation stay as they are** (`prog{ }` + `progOk`). The seed is the library dependency made explicit, not a uniform costume — ArrCatIota's concrete-index negative-control pair is untouched.
8. **Sweep the prose.** Reword doc-comment mentions of the old library so `grep StdLemmas <file>` ends empty — that grep is the fan-out's mechanical done-check.
9. **Capture needles by probe, not by guess.** Temporary in-file `#eval match checkProgramFrom Dllbc.std twin with | .ok _ => "OK" | .error e => e`, `lake build Dllbc.Tests.<X>` (native — `lake env lean` interprets the checker ~30×), transplant the message, delete the probe. The probe printing `OK` for an intended reject is the loudest possible flag that the twin was built wrong (see the `.unit` convention below).

### Twin replacements that reference the golden's binders

A twin's replacement term is built OUTSIDE any binding context, so references into the golden need care. Two techniques, by position:

- **Machine-side positions** (a borrow, a deref — anything the runtime walk resolves): write the var at id 0 — Ω resolution is name-keyed (`findSlot?` never reads an id), so the NAME is what binds: `ty{ &m * %(Dllbc.Term.var ⟨0, "kk"⟩) }` re-aims the exit at the sibling binder without knowing its minted id.
- **Type positions** (a pin instantiation): REUSE the honest subterms rather than reconstructing them. Extract the marked body (`markedBody?`, a two-line `mapMarkersGo` instantiation in the pilot), pattern-match its app spine, rebuild with the lie spliced in: `.app (.app (.app (.app (.app f n) ty{ Z }) ty{ Add %(i) %(r) }) res) sv` swaps two arguments and inherits `f`, `n`, `i`, `r`, `res`, `sv` — binder representation and all — from the golden itself.

Fallback branches in twin definitions return `.unit`, which CHECKS as a program — so a minting regression (marker renamed, spine shape changed) fails the twin's rejection pin loudly instead of passing it vacuously. Pair every twin with its `!= golden.term` pin anyway: it pins that the mutation landed.

### Gotchas (each one hit in the pilot)

- **A marker in a `fn` PARAMETER type occurs TWICE in the elaborated term.** `fnElab` reifies the signature into both the seal's Π domain and the body λ's domains, so `replaceMarked?` trips its exactly-one contract ("occurs 2 times") — loudly, as designed. Markers in RETURN types (MarkedTwins T3/T7) and in bodies occur once. The pilot's answer is a file-local `replaceMarkedN` (another `mapMarkersGo` instantiation) that replaces EVERY copy and returns the hit count, with the caller pinning the count — `| (2, t) => t` — so the loudness-on-drift survives. Both copies must be replaced (the audit reads the Π, the body carries the λ); promote the helper to `Syntax.lean` if a third file wants it.
- **`elabModule` is not `progOk`** — see recipe step 4. Dropping the old `progOk` on the strength of "the golden elaborates" silently sheds the `endScope` and return-audit halves of what the file used to assert.
- **σ indices in needles renumber wholesale.** The σ supply continues from the seed's `nextSym` (≈3.3k after the chain), so `σ₁` becomes `σ₃₃₁₀`. The message SHAPE is unchanged — the pilot's key-twin needle is the old one with indices renumbered, and its wrong-slot needle (written to avoid σ indices, pinning `"… declared pin (Pair (arrCat Z (S (natRec"`) survived verbatim. Prefer σ-free needles where the discriminating content allows; neither pilot needle weakened.
- **Marker extents parse bare where you want them.** `~> @slot (%PVSetDecT) n i r (*res) s)` marks the whole pin application (the borrow-type row's `~>` rhs is an unrestricted uterm; the spine's own parens don't delimit, the row's closing `)` does), and `=> @exit &m *vv }` marks the whole exit (arm bodies are unrestricted; `{` and `}` delimit). No extra parentheses needed in either.
- **The evidence mode question answers itself.** A call-and-bind `h1` is lowercase (linear, one read) and the carve reads it once — no CAPITAL premise needed at the consumer for the pilot's shape. The chain side already made 50 of 51 lemma premises capital (stage 6), so callers pass proofs in whichever mode they hold them.

### Composition-heavy citations: splice raws, not calls

Found by the fanout, the hard way (MatchJoin and SigmaCopy both had their first migrations reverted over it): **a chain-lemma call's result cannot feed another chain lemma's capital parameter.** A capital premise is read via ⇝, and `let h = LeAdd(a, b)` binds an existential minted at an ⇒ EVENT — ⇝ cannot read it, and the error says so (`readC (⇝): a call is not in the comptime fragment … a sealed or imperative callee must be entered, which is ⇒'s`). The minimal repro needs no `if`, no Σ-return, no second consumer: one call's result passed as another call's capital argument breaks by itself. So call-and-bind covers exactly two shapes — the result lands in a slot consumed by TYPE (recipe step 3), or a premise the fn already holds as its own parameter is passed along. It does not cover chained composition: lemma B consuming lemma A's result (SigmaCopy's `grow` is the extreme case, LeAdd→LeTrans→AddUC→IdSym→IdCongr→LeRwL→AddUC end to end).

The sanctioned form for composed chains is the one old StdLemmas gave for free: cite `Dllbc.StdChainRaw.*` — the raw constants are pure λ applications, fully ⇝-reducible, so nesting them costs nothing. MatchJoin's redo splices `(%(Dllbc.StdChainRaw.LebTrueLeRaw)) a b ev`; Arrays keeps five lemmas as genuine call-and-bind and takes scoped `open Dllbc.StdChainRaw` for the composed spots (bare raw names can fail to resolve — qualify or scope the open). This is an ingredient retarget, not a defeat: the composition being inexpressible as calls is the seal discipline working as designed, and the raws are part of the chain module precisely so composers have a ⇝-native citation.

One more finding from the same pair of failures, adjacent but distinct: **refinement threading stops at the first call.** A sealed call's comptime argument that depends on a match-arm refinement only propagates through pure application — when a chain call's result feeds a second sealed call, the refinement is already lost at the FIRST call. Same fix, same reason: keep refinement-dependent evidence in the pure fragment via raws.

### What did NOT need work

No placeholder resolution (the twins' calls were already retargeted in the persisted term; fresh `prog_parse` fragments' calls stay `.call` for the helpers to retarget). No seed threading through `%`-spliced file-local spec functions (`AllK7`, `AVSetT`, … keep their Lean-side `Term` defs and splices — they are the file's own vocabulary, not library citations). No assertion was dropped or merged: the pilot's 36 `native_decide`s became 38 (each old assertion 1:1, plus one `!= golden` pin per twin), with the four golden `def`s adding definition-site checks on top.
